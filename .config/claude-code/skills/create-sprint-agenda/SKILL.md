# スプリントプランニング アジェンダ作成

## 概要

前回議事録に記録された担当割り当てと GitLab の現在状態を突き合わせ、達成状況を集計する。
あわせてバックログを整理し、アジェンダを DocBase に draft で作成する。

会議後の記録は `record-sprint-plan` が行う。**この 2 つは対で動く。**片方だけを使うと次回の振り返りが空になる。

## 対象

| | |
| --- | --- |
| 議事録 | DocBase、グループ `Square`(29850) / `社員公開`(27865)、タグ `議事録` |
| Issue 管理 | `eseikatsu/es-account/account-service`、Milestone は `[ESA]` と `[LS]` |
| バックログ | `score-backlog` スキルに委譲 |
| テンプレート | `{skill_base_dir}/templates/agenda.md` |

会議は毎週木曜。Milestone は約 4 週なので、**両者の周期は一致しない**。
達成状況は Milestone 単位ではなく、前回議事録のスナップショットとの差分で出す。

## Step 1: 前回議事録を取得する

```
searchPosts(query: "title:スプリントプランニング desc:published_at", perPage: 5)
searchPosts(query: "title:スプリントプランニング is:draft desc:changed_at", perPage: 5)
```

**draft は既定の検索結果に含まれない。** 前回分が未公開のまま残っていることがあるため、両方を引いて会議日が直近のものを選ぶ。

選んだ記事を `getPost` で取得し、本文をファイルに落としてから担当割り当ての節だけを切り出す。

**本文全体から `#[0-9]+` を拾ってはいけない。** 議事録には振り返りの明細やバックログ節の issue 番号も載っており、節を切らずに抽出すると前回計画に混入する。

```bash
sed -n '/^# 担当割り当て/,$p' prev_post.md > prev_section.md
[ -s prev_section.md ] || sed -n '/^# プランニング/,/^# 担当割り当て/p' prev_post.md > prev_section.md
rg -o '#([0-9]+)' -r '$1' prev_section.md | sort -u > prev_iids.txt
wc -l prev_iids.txt   # 担当者ごとの表の件数合計と一致するか目視する
```

`# 担当割り当て` 節が無い議事録もある。`record-sprint-plan` を通さず手で書いた回は担当割り当てが `# プランニング` 節に入っているため、**そちらもフォールバックとして見る**（2026-08-06 の議事録が該当）。

どちらの節も無い場合だけ初回として扱い、Step 2 を飛ばして振り返り節に「前回の担当割り当ての記録がないため、次回から集計する」と書く。

**推移の履歴は議事録にない。** 振り返りダッシュボード（Artifact）の `HISTORY` 配列が正本なので、そちらを読む。
議事録の振り返り節から `claude.ai/artifact/` のリンクを拾い、`Artifact` ツールの `action: "read"` で開く。
返る HTML の `var HISTORY = [...]` がそのまま前回までの履歴で、ここに今回の 1 要素を足す。

```bash
rg -o 'https://claude\.ai/artifact/[A-Za-z0-9]+' prev_post.md | head -1
```

リンクが無い場合はダッシュボード導入前（2026-09-17 以前）の議事録なので、Step 2 の手順で過去 5 件の議事録から起こす。

## Step 2: 前回計画と現在を突合する

```bash
PROJ="eseikatsu%2Fes-account%2Faccount-service"
for M in "%5BESA%5D2026_08_25" "%5BLS%5D2026_08_25"; do
  glab api --paginate "projects/$PROJ/issues?milestone=$M&per_page=100"
done | jq -s 'add' > current.json
```

Milestone 名は Step 3 で決めた**現スプリント**のもの（次期ではない）。

各 issue を 6 区分に振り分ける。判定は上から順に当てる。

| 区分 | 判定 |
| --- | --- |
| 却下（未実施） | `却下` ラベルが付いている |
| 完了 | `state=closed`、または status が `ステージングアップ待ち` / `本番適用待ち` |
| 進行中 | status が `Doing` |
| 未着手 | status が `To Do` |
| 中止・除外 | `prev_iids.txt` にあるが現在 Milestone から外れた、または `status::backlog` へ戻った |
| 追加・割り込み | `prev_iids.txt` になく現在 Milestone にある |

status は account-service#4373 で 5 種（`backlog` / `To Do` / `Doing` / `ステージングアップ待ち` / `本番適用待ち`）に整理された。  
旧 status（`Done` / `MR` / `Feedback` / `検証中` / `テスト完了` / `品検待ち` / `リファインメント済`）は `deprecated::` 接頭辞へ退避済みで、open issue には付いていない。

**`却下` を完了に数えない。** 却下した issue は close されるため closed 判定では完了に混ざるが、実施していないのでベロシティには入らない。
`却下` は `status::` 接頭辞を持たない単独ラベルなので、status ラベルの走査では拾えない。判定順を closed より先に置く。

```bash
jq -r '.[] | select([.labels[]] | any(. == "却下")) | "#\(.iid)\t\(.title)"' current.json
```

**closed だけを完了にしない。** MR マージ時に `status::ステージングアップ待ち` へ移す運用があり、開発としての完了はその時点で到達している。closed 基準ではベロシティが実績の数分の一に見える。

ベロシティは完了区分の weight 合計。却下は含めない。

さらに**完了区分には前回スナップショット時点で既に完了へ到達していたものが含まれる**。
分離しないとベロシティが実態より大きく見える。前回の status を突合表に持ち、次の 2 つを併記する。

- 完了 weight 合計（現在の到達点）
- そのうち前回時点で未完了だったものの weight 合計（この 1 週間の増分）

2026-08-13 の実行では完了 32 件 / weight 30 のうち 17 件 / weight 17 が前回時点で既に到達済みで、増分は 15 件 / weight 13 だった。

区分ごとの明細（issue リンク・タイトル・担当・weight）を作る。
中止・除外には**理由を書く欄を空で置く**。会議で埋めるため。

**追加・割り込みに発生源の欄は置かない。** 会議で埋める運用にしたが使われなかった。
件数と weight、および内容の傾向（CI 系・機能系などの内訳）だけを示す。

### 集計はダッシュボードに集約する

**議事録に集計表を置かない。** その回だけの区分別集計は折りたたみの `<summary>` と二重になり、
推移の表もグラフと同じ数字を二度読ませる。**数字はすべてダッシュボード側に集約する。**

議事録の振り返り節に置くのは 3 つだけ。対象 Milestone の 1 行、ダッシュボードへのリンク、区分ごとの折りたたみ明細。
グラフを見れば分かる講評（ベロシティが何か、どの区分が伸びたか、担当別の残り）は書かない。

ダッシュボードは**表を持たない**。グラフから読み取れる数字を表で繰り返さない。
数値は棒の直接ラベルとホバーの `<title>` で読む。

履歴は `HISTORY` 配列が持つ。1 回 1 要素で、左が古く右が最新。

```js
{ label: "09-17", velocity: 44, days: 10, perday: 4.4, d: 10, t: 19, c: 26 }
```

`velocity` はその回のベロシティ（増分 weight）、`days` は営業日、`perday` は `velocity ÷ days`。
`d` / `t` / `c` はその時点で残っていた weight で、進行中 / 未着手 / 要確認。

**保持は直近 10 回まで。** 11 件目を足したら先頭を削る。それより古い回は傾向を読むのに使わないうえ、
運用や status の定義が変わっているため並べても比較にならない。

1 回は 1 週の議事録。Milestone は約 4 週なので途中で切り替わるが、**要素は分けない**。週次の増分として一列に並べる。

**`days` と `perday` を必ず入れる。** 会議が飛んだ週があると期間が倍になり、`velocity` だけでは前の回と比べられない。
`days` は前回議事録の翌日から当日までの土日祝を除いた日数、`perday` は小数第 1 位まで。

```bash
bizdays() {
  local d=$(date -d "$1 +1 day" +%Y-%m-%d) end="$2" n=0
  while [[ "$d" < "$end" || "$d" == "$end" ]]; do
    [ "$(date -d "$d" +%u)" -le 5 ] && n=$((n+1))
    d=$(date -d "$d +1 day" +%Y-%m-%d)
  done
  echo "$n"
}
bizdays 2026-09-03 2026-09-17   # 10
```

**祝日はこの関数では引けない。** 期間に祝日が入る回は手で減らし、グラフ下の所見に「08-13 の営業日 4 は 08-11 の山の日を除いた値」のように根拠を 1 行残す。

### グラフは Artifact に置く

数字の羅列では増減の向きが読み取れない。ダッシュボードを Artifact で作り、議事録からリンクする。
**DocBase の Mermaid では作れない。** `xychart-beta` は積み上げ棒に対応せず、y 軸も 1 本だけなので、グラフは Artifact 側に置く。

載せるのは 3 つ。**履歴を持つのは上の 2 つだけ**で、個人別は直近スプリントのぶんだけを出す。

- **ベロシティ推移** — 増分 W の棒（直近 10 回）
- **未完了の内訳推移** — 進行中 / 未着手 / 要確認 の積み上げ棒（直近 10 回）
- **個人別 未完了内訳** — 担当ごとの積み上げ棒（直近スプリントのみ、毎回入れ替え）

**二軸チャートを作らない。** 増分 W（13〜44）と W/日（3.3〜5.8）はスケールが 10 倍違う。
片方を 10 倍して重ねると相関を誤読させるため、W/日 は**同じ x 軸を共有する下段のパネル**に分ける。

グラフを書く前に `dataviz` スキルを読む。カテゴリ配色は blue `#2a78d6` / orange `#eb6834` / violet `#4a3aa7`（dark は `#3987e5` / `#d95926` / `#9085e9`）で、
`validate_palette.js` の light / dark 両方で全 PASS を確認済み。**色を変えたら必ず再検証する。**
aqua `#1baf7a` は light でコントラストが 3:1 を切り、表を持たない今の構成では relief rule を満たせないため使わない。

**個人別の数字は議事録の明細テーブルから集計する。** GitLab を引き直すと会議中の移動が反映され、
議事録の折りたたみ明細とグラフが食い違う。明細の担当列と W 列を区分ごとに合計すれば、当日の実績と一致する。

Artifact は**毎回同じ URL を更新する**（`action: "publish"` に前回の `url` を渡す）。新しいページを作らない。

手順は 4 つ。

1. `action: "read"` で現在の HTML を取る
2. `HISTORY` に今回の 1 要素を足し、11 件以上なら先頭を削る
3. `PEOPLE` を当日の集計でまるごと置き換える
4. 各セクションの `.note`（グラフ下の所見）を当日の内容に書き換え、同じ `url` へ publish する

**過去回の議事録から辿ると最新版が開く。** 当時の数字は Artifact のバージョン履歴にしか残らないため、
議事録には残らないことを承知で運用する。会議で参照するのは常に最新の推移なので、実務上は問題にならない。

議事録側はリンクだけにとどめる。担当別の未完了やベロシティを箇条書きで並べ直さない。グラフと重複する。

**過去の要素は前回のダッシュボードからそのまま引き継ぐ。数え直さない。**
当時の Milestone 構成と status は既に変わっており、今から再集計すると過去の数字が動いて推移が意味を失う。

ダッシュボードが無い回（この形式の導入前、2026-09-17 以前）は、過去の議事録を `searchPosts` で引き、
それぞれの区分別集計表と「ベロシティ: 完了 weight …」の箇条書きから 1 要素ずつ起こす。

### 明細は折りたたむ

**区分ごとの明細テーブルは `<details>` に入れる。** 見出しに件数と weight が出ていれば会議中に開く場面は限られる。
折りたたまないと記事の大半が明細で埋まり、集計表からバックログまで画面数回分のスクロールになる。

```markdown
<details>
<summary>完了（43 件 / weight 45）</summary>

| issue | タイトル | 担当 | MS | W | 前回 | 現在 |
| --- | --- | --- | --- | ---: | --- | --- |
| [#4590](...) | Renovate の更新ルールを調整する | 上屋誠 | ESA | 1 | — | 完了(closed) |

</details>
```

`<summary>` の直後と `</details>` の直前に空行を入れる。空行がないとテーブルがそのままの文字列で表示される。

**区分の明細はすべて折りたたむ。** 完了・進行中・未着手・却下・ステータス要確認・中止・除外・追加・割り込みの 8 つを同じ形にする。
中止・除外だけ開いておく運用にしていたが、体裁が揃わないため統一した。理由の欄は畳んだ中で埋める。

開いたままにするのはダッシュボードへのリンクだけ。会議の冒頭で見るのはグラフで、明細は必要になったときに開く。

## Step 3: Milestone を決める

```bash
G="groups/eseikatsu%2Fes-account"
glab api "$G/milestones?state=active" | jq -r '.[] | "\(.title)\t\(.start_date)\t\(.due_date)"'
```

現スプリント（Step 2 用）は due_date が実行日以降で最も近いもの、次スプリント（テンプレート用）はその次。

テンプレートに埋めるのは URL エンコード済みの文字列。

```bash
jq -rn --arg t "[ESA]2026_09_08" '$t|@uri'   # %5BESA%5D2026_09_08
```

**ESA / LS の Milestone 名は `[ESA]YYYY_MM_DD` / `[LS]YYYY_MM_DD` 形式**（例: `[ESA]2026_09_08`）。取得結果をそのまま信用せず、この形式に合っているかを検証する。

```bash
glab api "$G/milestones?state=active" \
  | jq -r '.[] | select(.title | test("^\\[(ESA|LS)\\]")) | select(.title | test("^\\[(ESA|LS)\\][0-9]{4}_[0-9]{2}_[0-9]{2}$") | not) | "命名規則違反: \(.title)"'
```

**規則違反の名前をそのままアジェンダへ運ばない。** 誤った名前で作られた Milestone があると、議事録・ボードリンク・次回の突合まで誤名が伝播する。
検出したら PO に確認のうえリネームし、正しい名前でアジェンダを組む。Issue の紐付けは milestone id 基準なので、リネームで壊れない。

```bash
glab api --method PUT "$G/milestones/<milestone id>" -f "title=[ESA]2026_09_29"
```

2026-09-03 の実行では `[ESA]20260929` / `[LS]20260929` が誤名のまま作られており、08-27 の議事録とボードリンクにもその名前で載っていた。
「API の結果から取る」だけでは誤名を検出できない。

## Step 4: バックログを整理する

`score-backlog` スキルを実行する。差分採点・ラベル運用・ボード整列・Artifact 更新まで含まれる。
採点結果は Wiki と優先度一覧の Artifact が正本で、会議ではテンプレートのリンクから開く。
**順位表や候補一覧をアジェンダに転記しない。** 会議で見るのは Artifact とボードで、議事録側の表は使われなかった。

アジェンダの `{{BACKLOG}}` に入れるのは、採点表から拾う次の 2 つだけ。どちらも前回議事録からの変化がある場合に限り、無ければ節ごと省く。

- **重複が疑われる組** — 前回から増えた・解消した組と、クローズできる条件を 1 項目ずつ
- **期日のあるもの** — `effort::期日あり` かつ Due date のある issue で、期日の近いものや扱いが変わったもの

```markdown
重複が疑われる組が 1 つ増えました。

- [#3098 本番環境の社内テスト法人の再整理](...)（180 位）は、10-05 に `[ESA]2026_10_13` の社内法人の整理（[#4676](...)〜[#4681](...)）と関連付けられました。後者で完了するなら #3098 はクローズできます

期日のあるもの:

- [#4034 AlloyDB のバージョンアップ](...)（Due 2026-10-31）は却下でクローズされ、対応は [#4298](...) に一本化されています
```

**生成したファイルの中身を読み、その文字列をそのまま使う。** 記憶で書き直さない。
issue のタイトルと根拠は本文を読まなければ書けない情報であり、書けてしまう場合は捏造している。

`score-backlog` は PO の承認を求める箇所があるため、この Step は対話が挟まる。
アジェンダ作成をまとめて流したい場合でも、ここは飛ばさない。

## Step 5: アジェンダを組み立てる

テンプレートを読み、プレースホルダを置換する。

| プレースホルダ | 値 |
| --- | --- |
| `{{RETROSPECTIVE}}` | Step 2 の対象 Milestone の 1 行・ダッシュボードのリンク・折りたたみ明細 |
| `{{BACKLOG}}` | Step 4 の重複疑い・期日ありの変化（無ければ空文字） |
| `{{COST_START}}` | 1 年前の当月 1 日 |
| `{{COST_END}}` | 今月末日 |
| `{{MS_ESA}}` `{{MS_LS}}` | Step 3 の次スプリント（URL エンコード済み） |

コスト URL の期間は**直近 13 か月**にする。見たいのは今月の着地予想で、前年同月と並べて初めて増減が読める。

```bash
date -d "$(date +%Y-%m-01) -1 year" +%Y-%m-%d          # {{COST_START}} 例: 2025-09-01
date -d "$(date +%Y-%m-01) +1 month -1 day" +%Y-%m-%d  # {{COST_END}}   例: 2026-09-30
```

`{{COST_END}}` は実行日ではなく**今月末日**。実行日で切ると月途中の実績だけが最終月に出て、着地との比較にならない。

置換後、`{{` が残っていないか検査する。

```bash
rg -n '\{\{' agenda_filled.md && echo "未置換あり"
```

## Step 6: DocBase に作成する

```
createPost(
  title: "YYYY/MM/DD Square 物件検索/メッセージ/アカウントサービス/ライセンスサーバ スプリントプランニング",
  body: <Step 5 の本文>,
  draft: true,
  scope: "group",
  groupIds: [29850, 27865],
  tags: ["議事録"]
)
```

日付は会議日。木曜当日の会議前に実行するため通常は実行日そのもの。引数で指定があればそれを使う。

**draft のまま残す。** 公開は PO の操作とする。

作成後、記事 URL と、会議で確認すべき点（中止・除外の理由）を報告する。

## 落とし穴

- **生成物を記憶で書き直さない**（Step 4）。issue のタイトルと根拠は読まなければ書けない。書けたなら捏造している
- 本文を DocBase へ送る前に、先頭と末尾の 1 行を確認する。混入した 1 文字が記事の先頭に残る
- `searchPosts` の既定結果に draft は含まれない。`is:draft` の検索を併用する（Step 1）
- 前回議事録の担当割り当ては `# 担当割り当て` に無いことがある。`# プランニング` 節もフォールバックで見る。どちらも無いときだけ初回扱いにして黙って進めない（Step 1）
- 本文全体から issue 番号を拾うと振り返りの明細やバックログ節の issue が混入する。節を切り出してから抽出する（Step 1）
- 完了判定を closed に置かない。`ステージングアップ待ち` 以降を完了とする（Step 2）
- `却下` ラベルの issue は closed だが未実施。完了と分けてベロシティから除く（Step 2）
- 日本語を含むラベルで `glab api "...?labels=..."` を叩くと HTTP 400 になる。`jq -rn '"effort::期日あり"|@uri'` でエンコードする
