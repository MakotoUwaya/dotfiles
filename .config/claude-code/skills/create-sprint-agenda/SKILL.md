# スプリントプランニング アジェンダ作成

## 概要

前回議事録に記録された担当割り当てと GitLab の現在状態を突き合わせ、達成状況を集計する。
あわせてバックログを整理し、アジェンダを DocBase に draft で作成する。

会議後の記録は `record-sprint-plan` が行う。**この 2 つは対で動く。**片方だけを使うと次回の振り返りが空になる。

## 対象

| | |
| --- | --- |
| 議事録 | DocBase、グループ `Square`(29850) / `社員公開`(27865)、タグ `議事録` |
| Issue 管理 | `eseikatsu/es-account/account-service`、Milestone は `[ESA]` と `[LS]` |
| バックログ | `score-backlog` スキルに委譲 |
| テンプレート | `{skill_base_dir}/templates/agenda.md` |

会議は毎週木曜。Milestone は約 4 週なので、**両者の周期は一致しない**。
達成状況は Milestone 単位ではなく、前回議事録のスナップショットとの差分で出す。

## Step 1: 前回議事録を取得する

```
searchPosts(query: "title:スプリントプランニング desc:published_at", perPage: 5)
searchPosts(query: "title:スプリントプランニング is:draft desc:changed_at", perPage: 5)
```

**draft は既定の検索結果に含まれない。** 前回分が未公開のまま残っていることがあるため、両方を引いて会議日が直近のものを選ぶ。

選んだ記事を `getPost` で取得し、本文をファイルに落としてから担当割り当ての節だけを切り出す。

**本文全体から `#[0-9]+` を拾ってはいけない。** 議事録にはバックログ上位 20 件の issue 番号も載っており、節を切らずに抽出すると前回計画に 20 件混入する。

```bash
sed -n '/^# 担当割り当て/,$p' prev_post.md > prev_section.md
[ -s prev_section.md ] || sed -n '/^# プランニング/,/^# 担当割り当て/p' prev_post.md > prev_section.md
rg -o '#([0-9]+)' -r '$1' prev_section.md | sort -u > prev_iids.txt
wc -l prev_iids.txt   # 担当者ごとの表の件数合計と一致するか目視する
```

`# 担当割り当て` 節が無い議事録もある。`record-sprint-plan` を通さず手で書いた回は担当割り当てが `# プランニング` 節に入っているため、**そちらもフォールバックとして見る**（2026-08-06 の議事録が該当）。

どちらの節も無い場合だけ初回として扱い、Step 2 を飛ばして振り返り節に「前回の担当割り当ての記録がないため、次回から集計する」と書く。

あわせて**前回議事録の推移表も切り出す**。Step 2 でその上位 4 行を今回の表へ引き継ぐ。

```bash
rg -N '^\| [0-9]{2}-[0-9]{2} \|' prev_post.md | head -4 > prev_trend.md
```

行が取れない場合は推移表の導入前（2026-09-17 以前）の議事録なので、Step 2 の手順で過去 5 件から起こす。

## Step 2: 前回計画と現在を突合する

```bash
PROJ="eseikatsu%2Fes-account%2Faccount-service"
for M in "%5BESA%5D2026_08_25" "%5BLS%5D2026_08_25"; do
  glab api --paginate "projects/$PROJ/issues?milestone=$M&per_page=100"
done | jq -s 'add' > current.json
```

Milestone 名は Step 3 で決めた**現スプリント**のもの（次期ではない）。

各 issue を 6 区分に振り分ける。判定は上から順に当てる。

| 区分 | 判定 |
| --- | --- |
| 却下（未実施） | `却下` ラベルが付いている |
| 完了 | `state=closed`、または status が `ステージングアップ待ち` / `本番適用待ち` |
| 進行中 | status が `Doing` |
| 未着手 | status が `To Do` |
| 中止・除外 | `prev_iids.txt` にあるが現在 Milestone から外れた、または `status::backlog` へ戻った |
| 追加・割り込み | `prev_iids.txt` になく現在 Milestone にある |

status は account-service#4373 で 5 種（`backlog` / `To Do` / `Doing` / `ステージングアップ待ち` / `本番適用待ち`）に整理された。  
旧 status（`Done` / `MR` / `Feedback` / `検証中` / `テスト完了` / `品検待ち` / `リファインメント済`）は `deprecated::` 接頭辞へ退避済みで、open issue には付いていない。

**`却下` を完了に数えない。** 却下した issue は close されるため closed 判定では完了に混ざるが、実施していないのでベロシティには入らない。
`却下` は `status::` 接頭辞を持たない単独ラベルなので、status ラベルの走査では拾えない。判定順を closed より先に置く。

```bash
jq -r '.[] | select([.labels[]] | any(. == "却下")) | "#\(.iid)\t\(.title)"' current.json
```

**closed だけを完了にしない。** MR マージ時に `status::ステージングアップ待ち` へ移す運用があり、開発としての完了はその時点で到達している。closed 基準ではベロシティが実績の数分の一に見える。

ベロシティは完了区分の weight 合計。却下は含めない。

さらに**完了区分には前回スナップショット時点で既に完了へ到達していたものが含まれる**。
分離しないとベロシティが実態より大きく見える。前回の status を突合表に持ち、次の 2 つを併記する。

- 完了 weight 合計（現在の到達点）
- そのうち前回時点で未完了だったものの weight 合計（この 1 週間の増分）

2026-08-13 の実行では完了 32 件 / weight 30 のうち 17 件 / weight 17 が前回時点で既に到達済みで、増分は 15 件 / weight 13 だった。

区分ごとの明細（issue リンク・タイトル・担当・weight）を作る。
中止・除外には**理由を書く欄を空で置く**。会議で埋めるため。

**追加・割り込みに発生源の欄は置かない。** 会議で埋める運用にしたが使われなかった。
件数と weight、および内容の傾向（CI 系・機能系などの内訳）だけを示す。

### 集計は 5 回分の推移で出す

**その回だけの区分別集計表は置かない。** 同じ数字が折りたたみの `<summary>` に出るため二重になる。
代わりに**直近 5 回の推移表**を 1 つ置く。増えているのか減っているのかは 1 回分の数字では読めない。

5 回は直近 5 週の議事録。Milestone は約 4 週なので途中で切り替わるが、**行は分けない**。週次の増分として一列に並べる。

| 議事録 | 営業日 | 完了 | 進行中 | 未着手 | 要確認 | 却下 | 計 | 追加 | 中止 | 増分 W | W/日 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 09-17 | 10 | 43 (45) | 11 (10) | 22 (19) | 17 (26) | 2 (1) | 95 (101) | 44 (43) | 2 (1) | 44 | 4.4 |
| 09-03 | 5 | 43 (47) | 4 (5) | 0 (0) | — | 2 (1) | 49 (53) | 14 (14) | 22 (17) | 23 | 4.6 |

セルは `件数 (weight)`。`増分 W` はその回のベロシティで、ここだけ weight 単独。
`追加` は追加・割り込み、`中止` は中止・除外。区分が存在しない回は `—`。

**`営業日` と `W/日` を必ず入れる。** 会議が飛んだ週があると期間が倍になり、増分 W だけでは前の回と比べられない。
`営業日` は前回議事録の翌日から当日までの土日祝を除いた日数、`W/日` は `増分 W ÷ 営業日`（小数第 1 位）。

```bash
bizdays() {
  local d=$(date -d "$1 +1 day" +%Y-%m-%d) end="$2" n=0
  while [[ "$d" < "$end" || "$d" == "$end" ]]; do
    [ "$(date -d "$d" +%u)" -le 5 ] && n=$((n+1))
    d=$(date -d "$d +1 day" +%Y-%m-%d)
  done
  echo "$n"
}
bizdays 2026-09-03 2026-09-17   # 10
```

**祝日はこの関数では引けない。** 期間に祝日が入る回は手で減らし、表の下に「08-13 の営業日 4 は 08-11 の山の日を除いた値」のように根拠を 1 行残す。

### グラフは Artifact に置く

表の数字だけでは増減の向きが読み取れない。ダッシュボードを Artifact で作り、議事録からリンクする。
**DocBase の Mermaid では作れない。** `xychart-beta` は積み上げ棒に対応せず、y 軸も 1 本だけなので、グラフは Artifact 側に置く。

載せるのは 3 つ。

- **ベロシティ推移** — 増分 W の棒
- **未完了の内訳推移** — 進行中 / 未着手 / 要確認 の積み上げ棒
- **個人別 未完了内訳** — 担当ごとの積み上げ棒（当日時点）

**二軸チャートを作らない。** 増分 W（13〜44）と W/日（3.3〜5.8）はスケールが 10 倍違う。
片方を 10 倍して重ねると相関を誤読させるため、W/日 は**同じ x 軸を共有する下段のパネル**に分ける。

グラフを書く前に `dataviz` スキルを読み、カテゴリ配色を `validate_palette.js` で light / dark 両方検証する。

**個人別の数字は議事録の明細テーブルから集計する。** GitLab を引き直すと会議中の移動が反映され、
同じ記事の中で推移表とグラフが食い違う。明細の担当列と W 列を区分ごとに合計すれば、講評の「担当別の未完了」と一致する。

Artifact は**毎回同じ URL を更新する**（`action: "publish"` に前回の `url` を渡す）。
当時の数字は議事録の推移表に残るため、過去回からリンクを辿って最新版が出ても記録は失われない。

議事録側はリンクと要点 2〜3 行にとどめる。担当別の未完了を箇条書きで並べ直さない。グラフと重複する。

**過去 4 行は前回議事録の推移表からそのまま引き写す。数え直さない。**
当時の Milestone 構成と status は既に変わっており、今から再集計すると過去の数字が動いて推移が意味を失う。

前回議事録に推移表が無い回（この形式の導入前、2026-09-17 以前）は、過去 5 件の議事録を `searchPosts` で引き、
それぞれの区分別集計表と「ベロシティ: 完了 weight …」の箇条書きから 1 行ずつ起こす。

表の下に、増分 W の傾向を 1 行で添える。週あたりのベロシティが落ちているか、割り込みが増えているかは会議の判断材料になる。

### 明細は折りたたむ

**区分ごとの明細テーブルは `<details>` に入れる。** 見出しに件数と weight が出ていれば会議中に開く場面は限られる。
折りたたまないと記事の大半が明細で埋まり、集計表からバックログまで画面数回分のスクロールになる。

```markdown
<details>
<summary>完了（43 件 / weight 45）</summary>

| issue | タイトル | 担当 | MS | W | 前回 | 現在 |
| --- | --- | --- | --- | ---: | --- | --- |
| [#4590](...) | Renovate の更新ルールを調整する | 上屋誠 | ESA | 1 | — | 完了(closed) |

</details>
```

`<summary>` の直後と `</details>` の直前に空行を入れる。空行がないとテーブルがそのままの文字列で表示される。

**折りたたむのは明細テーブルだけ。** 5 回分の推移表と箇条書きの所見は開いたままにする。
会議の冒頭で読むのはこの 2 つで、ここを畳むと振り返りが成立しない。

中止・除外の表も折りたたまない。理由の欄を会議で埋めるため、開いた状態で置く。

## Step 3: Milestone を決める

```bash
G="groups/eseikatsu%2Fes-account"
glab api "$G/milestones?state=active" | jq -r '.[] | "\(.title)\t\(.start_date)\t\(.due_date)"'
glab api "groups/eseikatsu%2Fes-square/milestones?state=active" | jq -r '.[] | "\(.title)\t\(.due_date)"'
```

現スプリント（Step 2 用）は due_date が実行日以降で最も近いもの、次スプリント（テンプレート用）はその次。

テンプレートに埋めるのは URL エンコード済みの文字列。

```bash
jq -rn --arg t "[ESA]2026_09_08" '$t|@uri'   # %5BESA%5D2026_09_08
```

**ESA / LS の Milestone 名は `[ESA]YYYY_MM_DD` / `[LS]YYYY_MM_DD` 形式**（例: `[ESA]2026_09_08`）。取得結果をそのまま信用せず、この形式に合っているかを検証する。

```bash
glab api "$G/milestones?state=active" \
  | jq -r '.[] | select(.title | test("^\\[(ESA|LS)\\]")) | select(.title | test("^\\[(ESA|LS)\\][0-9]{4}_[0-9]{2}_[0-9]{2}$") | not) | "命名規則違反: \(.title)"'
```

**規則違反の名前をそのままアジェンダへ運ばない。** 誤った名前で作られた Milestone があると、議事録・ボードリンク・次回の突合まで誤名が伝播する。
検出したら PO に確認のうえリネームし、正しい名前でアジェンダを組む。Issue の紐付けは milestone id 基準なので、リネームで壊れない。

```bash
glab api --method PUT "$G/milestones/<milestone id>" -f "title=[ESA]2026_09_29"
```

2026-09-03 の実行では `[ESA]20260929` / `[LS]20260929` が誤名のまま作られており、08-27 の議事録とボードリンクにもその名前で載っていた。
「API の結果から取る」だけでは誤名を検出できない。

Square は命名規則が異なる（`[Square]20260826`）。ESA / LS のパターンで推測せず、必ず API の結果から取る。

**次期の Square Milestone が未作成のことがある。** Square は ESA / LS と作成タイミングが違うため、`state=active` に現行分しか出てこない回がある。
その場合は現行を `{{MS_SQUARE}}` に入れ、アジェンダの Square 節に「次期 Milestone は未作成。この場で作成してからリンクを張り替える」と明記する。次期の名前を推測して URL を組まない。

## Step 4: バックログを整理する

`score-backlog` スキルを実行する。差分採点・ラベル運用・ボード整列・Artifact 更新まで含まれる。
採点は全件のまま Wiki が正本。**アジェンダに載せる件数だけを絞る。**

バックログ節は 2 部構成にする。**主役は棚卸しで、新規候補は従。**
会議の時間は `status::backlog` の整理に使う方針のため、新規候補は折りたたんで置く。

### 新規ピックアップ候補（上位 5 件）

`score-backlog` の Step 6 が出力する `top20.md` の**先頭 5 件**を `<details>` に入れる。

```markdown
<details>
<summary>新規ピックアップ候補（WSJF 上位 5 件）</summary>

| # | issue | WSJF | 判定根拠 |

</details>
```

20 件を開いたまま載せていた頃、会議で議論が及んだのは上位数件だけだった。

**生成したファイルの中身を読み、その文字列をそのまま使う。** 記憶で書き直さない。
issue のタイトルと判定根拠は本文を読まなければ書けない情報であり、書けてしまう場合は捏造している。

### status::backlog の棚卸し

こちらは折りたたまない。**判断欄を空で置き、会議で埋める。**

```bash
PROJ="eseikatsu%2Fes-account%2Faccount-service"
LBL=$(jq -rn '"status::backlog"|@uri')
glab api --paginate "projects/$PROJ/issues?labels=$LBL&state=opened&per_page=100" > backlog.json
```

対象は **Milestone 付きは全件、Milestone なしは WSJF 上位 5 件**。Milestone 付きを先に並べる。

| issue | タイトル | WSJF | Milestone | 担当 | W | 判断 |
| --- | --- | ---: | --- | --- | ---: | --- |
| [#4157](...) | Cloud Run Jobs に max-retries を統一設定して… | 12 | `[ESA]2026_09_29` | 上屋誠 | 1 |  |

**Milestone 付きの `status::backlog` は不整合。** 着手を決めて Milestone に入れたのに候補のままなので、振り返りの区分が「ステータス要確認」に落ちて集計が歪む。
毎回ゼロにするのが目標で、件数が多い回もそのまま全件出す。2026-09-17 時点で 15 件あった。

判断は `To Do` / `backlog 維持` / `却下` の 3 つ。会議後に `record-sprint-plan` が読んで反映する。
**アジェンダの時点でラベルを動かさない。** 格上げするかどうかがこの節の議題そのもので、先に動かすと議論の対象が消える。

**生成したファイルの中身を読み、その文字列をそのまま使う。** 記憶で書き直さない。
issue のタイトルと判定根拠は本文を読まなければ書けない情報であり、書けてしまう場合は捏造している。

採点表の列は `# | issue | 種別 | アウトカム | 放置リスク | 運用効率 | weight | WSJF | 判定根拠` の 9 列。
WSJF が 8 列目、判定根拠が 9 列目。

**`sed` の後方参照で列を並べ替えない。** 後方参照は `\9` までで、`\10` は「`\1` の後に文字 `0`」と解釈される。
9 列目を `\10` で拾うと判定根拠の欄に「順位 + 0」が入り、`60` `120` のような数字が並ぶ。2026-08-13 の実行で実際に踏んだ。

列の切り出しは `awk` で行う。

```bash
rg -N '^\| [0-9]+ \| \[#' prev_scores.md | awk -F' *\\| *' '{
  match($3, /#[0-9]+/); iid = substr($3, RSTART + 1, RLENGTH - 1)
  wsjf = $9; gsub(/\*/, "", wsjf)
  print $2"\t"iid"\t"$4"\t"$5"\t"$6"\t"$7"\t"$8"\t"wsjf"\t"$10
}' > prev_rank.tsv
```

`awk -F' *\\| *'` では行頭の `|` で `$1` が空になるため、**論理列 N は `$(N+1)`** になる。
抽出後、判定根拠の欄が日本語の文になっているかを先頭数行で目視する。数字が入っていたら列がずれている。

`score-backlog` は PO の承認を求める箇所があるため、この Step は対話が挟まる。
アジェンダ作成をまとめて流したい場合でも、ここは飛ばさない。

## Step 5: アジェンダを組み立てる

テンプレートを読み、プレースホルダを置換する。

| プレースホルダ | 値 |
| --- | --- |
| `{{RETROSPECTIVE}}` | Step 2 の集計表と明細 |
| `{{BACKLOG}}` | Step 4 の上位 20 件 |
| `{{COST_START}}` | 1 年前の当月 1 日 |
| `{{COST_END}}` | 今月末日 |
| `{{MS_ESA}}` `{{MS_LS}}` `{{MS_SQUARE}}` | Step 3 の次スプリント（URL エンコード済み） |

コスト URL の期間は**直近 13 か月**にする。見たいのは今月の着地予想で、前年同月と並べて初めて増減が読める。

```bash
date -d "$(date +%Y-%m-01) -1 year" +%Y-%m-%d          # {{COST_START}} 例: 2025-09-01
date -d "$(date +%Y-%m-01) +1 month -1 day" +%Y-%m-%d  # {{COST_END}}   例: 2026-09-30
```

`{{COST_END}}` は実行日ではなく**今月末日**。実行日で切ると月途中の実績だけが最終月に出て、着地との比較にならない。

置換後、`{{` が残っていないか検査する。

```bash
rg -n '\{\{' agenda_filled.md && echo "未置換あり"
```

## Step 6: DocBase に作成する

```
createPost(
  title: "YYYY/MM/DD Square 物件検索/メッセージ/アカウントサービス/ライセンスサーバ スプリントプランニング",
  body: <Step 5 の本文>,
  draft: true,
  scope: "group",
  groupIds: [29850, 27865],
  tags: ["議事録"]
)
```

日付は会議日。木曜当日の会議前に実行するため通常は実行日そのもの。引数で指定があればそれを使う。

**draft のまま残す。** 公開は PO の操作とする。

作成後、記事 URL と、会議で確認すべき点（中止・除外の理由、追加・割り込みの発生源）を報告する。

## 落とし穴

- **生成物を記憶で書き直さない**（Step 4）。issue のタイトルと根拠は読まなければ書けない。書けたなら捏造している
- 本文を DocBase へ送る前に、先頭と末尾の 1 行を確認する。混入した 1 文字が記事の先頭に残る
- `searchPosts` の既定結果に draft は含まれない。`is:draft` の検索を併用する（Step 1）
- 前回議事録の担当割り当ては `# 担当割り当て` に無いことがある。`# プランニング` 節もフォールバックで見る。どちらも無いときだけ初回扱いにして黙って進めない（Step 1）
- 本文全体から issue 番号を拾うとバックログ上位 20 件が混入する。節を切り出してから抽出する（Step 1）
- 完了判定を closed に置かない。`ステージングアップ待ち` 以降を完了とする（Step 2）
- `却下` ラベルの issue は closed だが未実施。完了と分けてベロシティから除く（Step 2）
- 表の列を `sed` の後方参照で並べ替えない。`\10` は `\1` + `0` になる（Step 4）
- 日本語を含むラベルで `glab api "...?labels=..."` を叩くと HTTP 400 になる。`jq -rn '"effort::期日あり"|@uri'` でエンコードする
- `createPost` は本文をインラインでしか受け取れない。生成物の読み込みと送信で本文がコンテキストに 2 回載るため、明細表を厚くするほど実行コストが上がる
- 一部だけ直すなら `patchPostBody` を使う。ただし**ローカルのファイルと投稿本文で行番号がずれる**（節を差し替えるスクリプトが空行を 1 行増減させるなど）。`oldContent` が 1 文字でも違うと 409 になるので、**1 行だけを同内容で置換する試験パッチでオフセットを確認してから**本番のパッチを送る
- ESA / LS の Milestone 名が `[ESA]YYYY_MM_DD` 形式かを検証する。誤名をそのまま運ぶと議事録とボードリンクに伝播する（Step 3）
- Square の Milestone は命名規則が異なる。API の結果から取る（Step 3）
- 画像は貼らない。ロードマップも SendGrid も URL リンクにする。前回の議事録を複製する運用では古い画像が残り続けた
- コスト URL の期間は 1 年前の当月 1 日から今月末日までの 13 か月。年度始まり固定にも実行日締めにもしない（Step 5）
- GCP のコスト URL から `rapt` / `pli` を落とす。ブラウザのアドレスバーから取ると再認証トークンが付いてくる。議事録は社員公開のため残さない
- 振り返りの明細テーブルは `<details>` で畳む。推移表・所見・中止除外の表は畳まない（Step 2）
- その回だけの区分別集計表は置かない。直近 5 回の推移表 1 つにする。過去 4 行は前回議事録から引き写し、再集計しない（Step 2）
- 推移表に `営業日` と `W/日` を欠かさない。会議が飛んだ週があると増分 W だけでは比較できない。祝日は手で引く（Step 2）
- グラフは Artifact に置き、議事録にはリンクと要点 2〜3 行だけ。DocBase の Mermaid は積み上げも二軸も描けない（Step 2）
- 二軸チャートを作らない。W/日 は棒に重ねず下段のパネルへ分ける（Step 2）
- グラフの数値は議事録の明細から集計する。GitLab を引き直すと会議中の移動で表と食い違う（Step 2）
- バックログの新規候補は上位 5 件だけを折りたたんで載せる。開いたまま並べるのは `status::backlog` の棚卸し（Step 4）
- 棚卸しの判断欄はアジェンダ時点で空にする。ラベルを先に動かすと議題そのものが消える（Step 4）
