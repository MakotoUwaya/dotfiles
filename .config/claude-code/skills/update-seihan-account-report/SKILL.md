# 製販本会報告 アカウントサービス更新

## Overview

月次の製販本会報告資料（DocBase、織田さん作成）のうち、自分が担当するアカウントサービス（ESA）・ライセンスサーバ関連の記述と投資状況テーブルを、直近の実績・進捗で更新する。

記事は他メンバーの所有物なので、**変更案を提示してユーザーの承認を得てから** `patchPostBody` で最小差分を反映する。

## When to Use

- 製販本会（月次）の前に報告資料へアカウントサービスの近況を反映するとき
- トリガー例: 「製販報告を更新して」「製販本会資料にアカウントサービスの更新内容を反映して」

## 前提知識: 記事の構造

「アカウントサービス・ライセンスサーバの開発」という単一見出しは**存在しない**。更新対象は以下の 3 箇所に分散している。

| 箇所 | 見出し | 内容 |
|---|---|---|
| 冒頭 | `## 開発トピックス` の `* アカウントサービス` | 2〜3 行のハイライト。本文セクションと整合させる |
| `## 開発` > `### 投資状況` | `#### 対応中` テーブル | PR コード別の当初予定・現在（着地値） |
| `## 開発` > `### 開発` | `#### アカウントサービス *`（基盤拡張 / デスクトップアプリ Auth0 対応 / MFA・Passkeys 対応 / 管理機能拡充 / ロードマップ検討 等）と `#### 品質維持 20XX NQ` 内の `- アカウントサービス` | 各テーマの概要・進捗・スケジュール |

- ライセンスサーバの独立セクションは通常置かない（過去に提案して見送り）。特筆事項があれば品質維持セクション等に含める
- セクション構成は号ごとに変わるため、必ず最新本文を読んで現状の見出しを確認してから差分を設計する

## Instructions

### Step 1: 対象記事と情報源の取得

必要な MCP ツールのスキーマを最初に ToolSearch でまとめてロードする（getPost / searchPosts / patchPostBody / slack_search_public_and_private / download_file_content）。

1. **対象記事**: ユーザー提示の URL/メモ ID を使う。無ければ `searchPosts` で `title:製販本会報告 いい生活Square desc:published_at` を検索し、タイトル日付が最新のものを選びユーザーに確認する
2. `getPost` で本文を取得し、現状のアカウントサービス関連記述を把握する
3. **最新の週次報告書**: `searchPosts` で `group_id:33891 tag:週次報告書` から、タイトル `（YYYY/MM/DD）` が最新のものを `getPost`。Square セクションの「アカウントサービス」「ライセンスサーバ」を材料にする
4. **自分の Slack 発言**: 週次報告書の日付以降を対象に検索する。**結果過大エラーを避けるため必ず `response_format: 'concise'`, `include_context: false`, `sort: 'timestamp'` を指定**する

   ```
   query: from:<@U223M954Z> ESA after:YYYY-MM-DD
   ```

   ESA のほか MFA / Passkeys / Auth0 / ライセンスサーバ などテーマ別に小さく分けて検索する
5. **アクティビティサマリ**: `works/activity-summary/YYYYMM/DD.md`（絶対パス推奨、リポジトリ直下に同名 `works/` があるため `works/works/...` になる点に注意）のうち、週次報告書の日付以降の日を読む

### Step 2: 変更案の作成と承認

- 本文を書く前に `docbase-markdown` スキルを参照する
- セクションごとに「変更後の Markdown 全文＋変更点の説明」を提示し、情報源（週次報告書 / Slack / サマリ）を明記する
- 古くなった記述（例: 「展開停止中」→ 段階展開再開済み）は現状ベースに書き換える。ただしトラブル等の解消状況が情報源から確定できない場合は、削除せずユーザーに確認する
- 日付は `M/D(曜)` 表記。**曜日は必ずカレンダーで検算**し、情報源にない日付・曜日を推測で書かない
- ユーザーの修正指示を反映し、承認を得てから Step 4 へ進む

### Step 3: 投資状況テーブルの更新（承認後、依頼された場合）

データソースは**ロードマップ Spreadsheet の着地値**（`eseikatsu-product-docs:update-weekly-reports` スキルと同方式）。週次報告書の数値の転記や `scripts/fetch_project_monitor.cjs` は使わない。

1. `mcp__claude_ai_Google_Drive__download_file_content` を `fileId: 15KBwPi1BHCY8YuhGtqDDgPVvvmf1QDYSKTaNRBlIJXc`, `exportMimeType: text/csv` で呼ぶ。結果は退避ファイルに保存される
2. base64 デコードは **Python で行う**（bash の `base64 -d` は invalid input になる）:

   ```bash
   python -c "
   import json, base64
   data = json.load(open(r'<退避ファイル>', encoding='utf-8'))
   open(r'<scratchpad>/roadmap.csv', 'wb').write(base64.b64decode(data['content']))
   "
   ```

3. **既存テーブルの PR コード起点で更新しない**。CSV から `プロダクト列(index 2) in (Square, アカウント)` の PR コード行（`PJコード列(index 17)` が `PR\d{8,10}`）を全件抽出し、ステータスで仕分ける:
   - `ステータス(index 11) == 対応中` → テーブルに載せる（**新規開始 PJ の追加漏れ・対応済への変化を両方検出できる**）
   - `対応済` へ変わった PJ はテーブルから外し、ユーザーに報告する
4. 主要列（CSV 0-origin）: 2=プロダクト, 4=TGR, 5=ロードマップアイテム, 11=ステータス, 14=初期計画予定開発時間, 16=初期計画予定投資額, 17=PJコード, 18=着地工数, 19=着地金額, 20/22=開始日, 21/23=終了日
5. 分類は TGR 列から: `変革`=T, `成長活動（ビジネスの拡大）`=G, `運営活動（ビジネスの保護）`=R。行順は G → T → R
6. 表記ルール:
   - PR コードには **Google Apps Script リンクを維持する**（週次報告書のプレーンテキスト方式とは異なる。金額更新時にリンクを外さない）
     - 既存行のリンク URL（特に `highlight` パラメータ）は**一切変更しない**
     - `highlight` は Apps Script 側で管理されている名称と**完全一致が必要**。PJ 名やロードマップアイテム名からの推測で組み立ててはいけない
     - 新規 PJ の行を追加する場合は、**ユーザーに質問して正確な highlight 名称を入手**してからリンクを作る（URL 形式: `https://script.google.com/a/macros/e-seikatsu.co.jp/s/AKfycbxPEoZpsPeFaR1_cmKardLoF6byyAF7i5xD-Bfke-fq5OChesqjZj4nf0FP4EIEElA/exec?product={Square|アカウント}&highlight={入手した名称}`）。回答が得られるまでは変更案にプレースホルダである旨を明記する
   - プロジェクト名は PJ コードだけで分からないよう、プロダクト名を含む名称にする（例: `アカウントサービス MFA 全法人展開・Passkeys 導入`）
   - セル書式は `￥1,234,567<br>123.4h`（金額 3 桁カンマ、時間小数 1 桁）
   - 合計行（当初・現在の金額/時間）を再計算し、**構成 PJ の単純合計と一致するか検算**する
7. 後始末: 退避ファイルと `roadmap.csv` を削除する

### Step 4: DocBase への反映

1. **反映直前に `getPost` で最新本文を再取得**する（他メンバーが編集している可能性が高い。取得済み本文をそのまま信用しない）
2. `patchPostBody` で行単位の最小差分を適用する:
   - 行番号は再取得した本文を `\r\n` で分割して数える。`oldContent` は完全一致が必要（末尾スペースも保持）
   - 複数箇所は 1 回の呼び出しに operations をまとめる（アトミック適用）
   - 409 Conflict が返ったら `getPost` で再取得し、行番号と oldContent を作り直してリトライする
3. `updatePost`（全文置換）は使わない。他メンバーの編集を巻き戻すリスクがある

### Step 5: 完了報告

- 更新箇所の一覧と各変更の要旨
- 投資状況を更新した場合: 追加/除外した PJ（コード＋名称）、合計値、検算結果
- データの基準日（週次報告書の日付、Spreadsheet 取得日時）

## Examples

### 投資状況テーブル行の更新例

Before（古い実績・新規 PJ 漏れ）:

```markdown
| G | [PR00009151](https://script.google.com/...?product=Square&highlight=外部連携対応+2026+上期) | 外部連携対応 2026 上期（内見/申込） | ￥2,460,000<br>500.0h | ￥742,945<br>157.9h |
```

After（既存行はリンクをそのまま維持して着地値のみ更新。新規 PJ の highlight はユーザーから入手した名称を使う）:

```markdown
| G | [PR00009151](https://script.google.com/...?product=Square&highlight=外部連携対応+2026+上期) | 外部連携対応 2026 上期（内見/申込） | ￥2,460,000<br>500.0h | ￥1,412,212<br>292.4h |
| G | [PR00009501](https://script.google.com/...?product=アカウント&highlight={ユーザーに確認した正確な名称}) | アカウントサービス MFA 全法人展開・Passkeys 導入 | ￥3,035,500<br>500.0h | ￥295,293<br>59.4h |
```

NG 例: `highlight=MFA+全法人展開` のように PJ 名から推測して組み立てる。管理名称と一致しないとハイライトが機能しない。

あわせて報告する内容の例:

> PR00009191（Square物件検索 掲載物件数増加取込対応）は Spreadsheet でステータス「対応済」になっていたため対応中テーブルから外しました。

## Guidelines

- 記事は他メンバーの所有物。**承認前に反映しない**。承認後も追加の書き換えがあり得る前提で、反映のたびに最新を取得する
- 変更案には必ず情報源を添え、情報源にない内容（解消状況・日付・件数）を創作しない
- 既存の URL・リンクパラメータ（特に `highlight`）は書き換えない。不明な値は推測せず、ユーザーに質問して正確な値を入手する
- 検討初期段階のトピックを載せるかは粒度の判断が分かれる。迷ったら変更案の補足でユーザーに確認する（例: 非アクティブアカウント削除は「関心が高いので必ず含める」だった）
- 一時ファイルは scratchpad ディレクトリを使い、終わったら削除する
