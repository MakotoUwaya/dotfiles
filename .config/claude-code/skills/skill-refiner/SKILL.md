# Skill Refiner

## Overview

`skill-creator` は **新規スキル作成** 用、本スキルは **既存スキル改善** 用。
日々スキルを使う中で見つかった摩擦・齟齬を、SKILL.md にピンポイントで反映する。

例として今日のセッションで実施した改善:
- `end-work` / `summarize-visit-reports` / `generate-activity-summary` に **「Shell 別実行ガイド」** 追加
- `mcp__teamspiritMcp__*` → `mcp__teamspirit__*` への **MCP ツール名更新**
- `mcp__docbaseMcp__*` → `mcp__docbase-mcp__*` への **DocBase ツール名更新**
- `gcal_list_events` → `list_events` への **Calendar ツール名更新**
- Redmine MCP 廃止に伴う **REST API 直接呼び出しへの差し替え**
- `pkill` → PowerShell `Get-CimInstance + Stop-Process` 併記

## When to Use

- スキル実行中にエラー・違和感が出た（ツールが見つからない、パスが効かない、状態遷移が網羅されていない等）
- 利用者が「このスキル古い情報がある」と指摘した
- 環境変化（MCP 構成変更、シェル変更、ツールリネーム等）に追随したい
- 月次・四半期等のスキル棚卸し

## Instructions

### Step 1: 対象スキルの特定と現状把握

ユーザーから対象スキル名を受け取る（複数可）。または「最近うまく動かなかったスキル」を聞く。

```bash
# プロジェクトスキルとユーザースキルの両方を確認
ls .claude/skills/<skill-name>/
ls ~/.claude/skills/<skill-name>/
```

SKILL.md を Read して全文を頭に入れる。

### Step 2: 摩擦点の収集

以下の3つのソースから問題を抽出する:

1. **直近のセッション** — そのスキル実行中にどんなエラー・回り道が起きたか
2. **ユーザーからの明示的な指摘** — 「ここがズレてる」「これは古い」等
3. **下記のチェックリスト** — 機械的に当てはめる

#### 点検チェックリスト

| 観点 | チェック項目 |
|------|------------|
| **MCP ツール名** | サーバー側のリネーム（`xxxMcp` → `xxx-mcp`、`gcal_*` → `*` 等）を反映しているか |
| **MCP の存在前提** | 実際には接続されていない MCP に依存していないか（公式無し → API 直叩きへ差し替え） |
| **Shell 依存** | bash だけでなく PowerShell でも動く例示・読み替え表があるか |
| **ハードコードパス** | `/tmp` `~/.config/...` 固定でなく、`Path.GetTempPath()` / `$env:TEMP` 等のポータブル指定 |
| **dotnet スクリプト呼び出し** | `~/.config/...` のチルダ展開で `dotnet` がパスを誤認するバグ → プロジェクトローカル相対パス推奨 |
| **状態遷移マトリクス** | （例: 出退勤の組み合わせ）未登録/打刻済みの全パターンが網羅されているか |
| **PJコード／枝番** | アクティブな PJ 一覧と整合（categories.md と乖離していないか） |
| **引数フォーマット** | doc に書かれた引数例と実際の挙動が一致しているか |
| **エラーリカバリ手順** | 想定エラーごとの対処が明記されているか |
| **前提条件** | VPN 必須・ログイン必須・パッケージ事前インストール等の前提が冒頭に書かれているか |
| **依存スキルの参照** | 連携する他スキル名・ファイルパスが現状と合っているか |
| **コミットメッセージ／Slack 文言** | 例示が現行ルールと一致しているか |

### Step 3: 改善案の整理と提示

抽出した問題を「**修正前 → 修正後**」の形でユーザーに提示する。

- 影響範囲が広い変更（破壊的）はユーザーに事前承認を取る
- 単純な誤記・ツール名追従などは確認なしで適用可（auto mode 時）

### Step 4: 編集

- **Edit ツール**でピンポイント修正（Write 全置換は避ける）
- 既存の構造・トーンを尊重する。**全面書き換えは禁止**
- セクション追加が必要な場合は、関連セクションの直後に挿入する

### Step 5: 検証

- `skill-checker` スキル（あれば）で SKILL.md の構文・命名・description 品質をチェック
- 実際にスキルを再実行して挙動が改善したか確認（可能な場合）
- 関連スキル（依存される側）もリネーム等の影響を受けていないか grep で確認

```bash
# 例: 旧ツール名が他スキルに残っていないか
rg "mcp__teamspiritMcp__" ~/.claude/skills/ .claude/skills/
```

### Step 6: 反映ログの残し方

- プロジェクト内のスキル変更は通常通り `commit-and-push` で記録
- ユーザー側スキル（`~/.claude/skills/`）はそのまま保存（dotfiles 管理下なら別途）
- 大きい変更は CLAUDE.md の関連箇所も同期させる（環境セットアップ・利用可能なSkills 等）

## Examples

### Example 1: MCP ツール名のリネーム追従

**症状**: `end-work` 実行時、`mcp__teamspiritMcp__getAttendance` が見つからない。実際には `mcp__teamspirit__getAttendance` にリネームされていた。

**対応**:
1. SKILL.md 内の旧名を全置換（`replace_all: true` の Edit）
2. ToolSearch クエリも更新
3. 関連スキル（`generate-activity-summary` 等）も同様に grep & 置換

### Example 2: PowerShell 対応

**症状**: PowerShell から `> /tmp/foo.json` がエラー（`/tmp` が `C:\tmp\` と解釈される）。

**対応**:
1. SKILL.md 冒頭に「Shell 別実行ガイド」セクション追加
2. 主要コマンドの bash / PowerShell 併記版を追加
3. `pkill` 等の Linux 専用コマンドに PowerShell 等価版を併記

### Example 3: 状態遷移漏れの追加

**症状**: `end-work` で「出社打刻済み・退社未打刻」のケースが状態マトリクスに無く、判断ミスをした。

**対応**:
1. 該当テーブルに行追加
2. 既存出社時刻を保ったまま `editAttendance` で退社のみセットするロジック例を追加
3. `forceOverwrite` の必要性についても注意書き

## Guidelines

- **追加優先・削除控えめ**: 古い記述でも、別環境では有効な可能性がある。基本は併記する形で対応する
- **一度に全部直さない**: 1 PR / 1 セッションで扱う観点を絞る。広すぎる変更はレビュー困難
- **背景を残す**: なぜ変更したか（旧構成との違い・遭遇したエラー）を簡単にコメントまたはコミットメッセージに残す
- **構造を崩さない**: 既存の見出しレベル・テーブル列順を尊重する。Diff が読みやすくなる
- **検証可能な修正のみ**: 推測ベースの「たぶんこうだろう」改変は避け、実セッションで確認できた事象のみ反映する
- **`skill-creator` との使い分け**:
  - 新規パターンを汎化したい → `skill-creator`
  - 既存スキルが古い／動かない → 本スキル
- **`superpowers:writing-skills` との使い分け**: あちらは新規作成・全般的な編集・デプロイ前検証。本スキルは「実運用での摩擦解消」に特化したチェックリスト主導のリファイン
