# Alert Triage - アラート評価と報告

## Overview

監視システムが発報したアラートを評価し、対応要否の判断材料を Slack に投稿する。
コアフロー（本ファイル）はアラートソースに依存しない。
ソース固有の調査コマンドは `resources/<source>.md` に分離し、新しいソースはファイル追加だけで対応できる。

## When to Use

- Slack のアラートチャネルに届いた通知の内容評価を依頼されたとき
- 「このアラート何？」「対応必要？」「影響ある？」と聞かれたとき
- アラートの一次切り分け（トリアージ）を行うとき

## ソース別調査手順

アラートの通知元・リンク URL から調査手順ファイルを選択する。

| ソース | 判定基準 | 手順ファイル |
|--------|---------|-------------|
| GCP (Cloud Monitoring / Service Health) | `console.cloud.google.com/monitoring` へのリンク | `resources/gcp.md` |

未対応ソースの場合はその旨をユーザーに伝え、リンク先 URL・通知本文から取得できる範囲で評価する。

## Instructions

以下の手順を順番に実行する。**ステップ 2〜4 は必ず証拠（コマンド出力・ログ）を取得してから次に進む**こと。推測で影響判断しない。

### 1. アラートメッセージの読み取り

- Slack メッセージ URL から channel_id / message_ts を抽出し、`slack_read_thread` でスレッドごと読む
- スレッド返信に既存の対応記録がないか確認する
- **本文が文字数制限で省略されている場合**（例: "The text was omitted because it exceeded 3000 characters"）、Slack からは詳細が取れない。ソース側 API での調査に切り替える

### 2. 発火元と発火条件の特定

ソース別手順ファイルに従い、以下を特定する:

- どのアラートポリシー / ルールが発火したか
- 発火条件（フィルタ・しきい値・除外設定）
- **発火時刻とソース側イベントの突合**: アラート発報時刻（タイムゾーン注意。Slack 表示は JST、ソース側ログは UTC が多い）とイベントログのタイムスタンプを照合し、対象イベントを一意に特定する

### 3. イベントの現在状態確認

- イベント / 障害が現在も継続中か、解消済みかを確認する
- 解消済みの場合は解消時刻と原因（プロバイダ発表があれば）を記録する

### 4. 実影響の証拠ベース確認

「影響がありうる」ではなく「影響があったか」を確認する:

- 影響範囲（対象機能・対象リージョン）と自システムの利用状況を突合する
- 当該時間帯に影響対象の操作・処理が実行されたかをログ（監査ログ・アプリログ）で確認する
- 異常値の判断が必要な場合は、平常時ベースラインと公式仕様を先に確認する

### 5. 評価文面の作成

3 部構成で作成する:

```
**アラート評価: <件名>**

*概要*
- 発報日時・発火したアラート名・対象プロジェクト/環境
- 何が起きたか（イベント ID があれば併記）
- 現在の状態（継続中 / 解消済み + 解消時刻・原因）

*影響懸念*
- 影響範囲（対象機能・リージョン）
- 自システムへの実影響の有無と、その根拠（確認したログ・期間）

*緊急性評価*
- 対応要否の結論（対応不要 / 経過観察 / 要対応 + 期限）
- 結論の根拠
```

### 6. 投稿確認と Slack 投稿

1. 評価文面を会話上でユーザーに提示する
2. `AskUserQuestion` で投稿先（スレッド返信 / チャネル新規投稿 / 投稿しない）を確認する
3. 承認後 `slack_send_message` で投稿し、メッセージリンクを報告する
4. 投稿後、評価の根拠（確認したコマンド・ログ）のサマリを会話上で報告する

## Examples

入力:

> アラートの内容を評価して、Slack チャネルに投稿してください
> https://example.slack.com/archives/C0XXXXXXX/p1780509778925959

出力（投稿文面の例）:

> **アラート評価: Cloud Firestore 障害（Service Health）**
>
> *概要*
> - 6/4 03:02 JST 発報の「Confirmed relevant incidents」アラート（stage / prod 両プロジェクトで発火）
> - Google Cloud 側の Firestore 障害（incident `YWRCLBM`）で、restore / clone 操作でエラーが発生する可能性
> - 発生 6/4 02:35 JST → 解消 6/4 04:04 JST（解消済み）
>
> *影響懸念*
> - 影響範囲は Firestore の restore / clone 操作のみで、通常の読み書きには影響なし
> - 監査ログを確認した結果、直近 48 時間に restore / clone 操作の実行はなく、実影響なし
>
> *緊急性評価*
> - 対応不要（プロバイダ側で解消済み・実影響なし）

## Guidelines

- **証拠が先、判断が後**: 再現確認・ログ収集を踏まえてから評価を書く。確度の低い仮説で「影響あり」と書かない
- **タイムゾーンの突合を省略しない**: 発報時刻とイベント時刻の照合は対象イベント特定の要。JST/UTC の変換ミスに注意
- **投稿前確認は必須**: 外部公開となる Slack 投稿は、必ず文面提示 + AskUserQuestion の承認を経る
- **「解消済み」でも影響確認は行う**: 障害発生中に自システムが影響操作を実行していた可能性は残る
- 緊急性評価の優先度は、観察された現象の規模で判定する（アラートの severity 表示だけで判断しない）

## 新しいアラートソースの追加方法

1. `resources/<source>.md` を作成し、以下を記載する:
   - 発火元アラートルールの特定方法（CLI / API コマンド）
   - 発火時刻とイベントの突合方法
   - イベント状態の確認方法
   - 実影響確認に使うログの参照方法
2. 本ファイルの「ソース別調査手順」表に判定基準と手順ファイルを追加する
