# 調査サブエージェント用プロンプト

`<REPO_PATH>` を対象リポジトリの絶対パスに、`<STACK>` を技術スタック説明に置換して
Explore サブエージェント（search breadth: very thorough）に渡す。
2 つは 1 メッセージで並列起動する。

## リポジトリ種別ごとの読み替え（汎用ルール）

調査プロンプトの適用方法はリポジトリ名ではなく**種別**で決める。
グループ・プロジェクトを問わず、まず種別を判定してから対応する読み替えを適用する。

| 種別 | 判定基準 | 読み替え |
|---|---|---|
| コード（アプリ / ライブラリ） | package.json / Cargo.toml / go.mod 等のマニフェストがある | 読み替えなし。調査 A + B をそのまま実行 |
| IaC（Terraform 等） | `*.tf` が主体 | 調査 B の「テスト」= `terraform validate` / `plan` / tflint / trivy(tfsec 系) / conftest / terratest 相当と読み替える。「バージョンアップ」= Terraform 本体・provider・module。**手動 apply ゲートの有無を必ず確認**する |
| 文書 | コードが無い（手順書・テンプレート等が主体） | 調査 B を調査 B'（文書棚卸し）に置き換える。調査 A は §5〜6 相当（.claude/・ルール文書）を中心に実行 |

混在リポジトリ（例: コード + IaC ディレクトリ）は主体側の種別で実行し、
従属側の観点（apply ゲート等）をプロンプトに追記する。
リポジトリ固有の事情（調査範囲の限定等）は `target-repos.md` を参照する。

## 調査 A: ハーネス構成

```
対象リポジトリ: <REPO_PATH>（<STACK>）

このリポジトリの「AI エージェント開発ハーネス」構成要素を very thorough に調査し、事実を列挙してください。調査対象:

1. リポジトリ全体構造: ワークスペース/モジュール構成、ディレクトリごとの役割
2. 主要依存のバージョン: 言語ランタイム・フレームワーク・主要ライブラリ（Terraform の場合は本体/provider/module）の実バージョン。メジャーバージョン遅れの可能性があるものを特定
3. CI 構成: CI 定義ファイルのジョブ一覧（lint, test, build, coverage, scan, deploy, schedule 等）と、各ジョブが何を強制しているか。手動承認ゲートの有無
4. ガードレール: pre-commit hooks（husky/lefthook/core.hooksPath）、lint-staged、commitlint/gitmoji 設定、renovate.json の設定内容（automerge・major の扱い）、GateGuard 関連設定
5. .claude/ ディレクトリ: rules/（paths frontmatter の有無と対象）、skills/ 一覧と概要、hooks/ と settings 内 hooks 定義、agents/（サブエージェント定義）の有無、settings の permissions・plugins
6. RULES.md / CLAUDE.md / GEMINI.md の内容概要。CLAUDE.md が規約文書・ナレッジへのポインタ参照になっているか（人間向け文書とエージェント向け注入の分離状況）
7. コード生成・型生成の仕組み: SSoT と派生物の関係（OpenAPI→型、スキーマ→エンティティ、リモートスキーマ→生成物等）。生成物が最新かを CI が検証しているか（drift チェックの有無）
8. サブエージェント定義: 調査用・実装用・レビュー用など目的別のサブエージェント定義（.claude/agents/）の有無。skills がサブエージェント委任を前提にした構成か

出力: 事実のみを構造化して返す。ファイルパスを明記。バージョン番号は実際の値を記載。
```

## 調査 B: テスト現状（コードを持つリポジトリのみ）

```
対象リポジトリ: <REPO_PATH>（<STACK>）

このリポジトリのテストの現状を very thorough に調査してください。目的は「依存パッケージ・フレームワークを安全にバージョンアップできるようにするためのテスト拡充計画」の材料集めです。

調査対象:
1. モジュール/パッケージごとのテスト有無と規模: テストファイル数とソースファイル数の比、テストフレームワーク
2. テストの種類: unit / integration / E2E / snapshot / 契約テスト / visual regression の有無
3. カバレッジ計測の有無と設定、CI でのカバレッジゲート（表示のみか、閾値で fail するか）
4. テストが薄い・全く無いモジュールの特定（src : test 比を概算）
5. E2E やスモークテストの有無（主要画面・エンドポイント疎通）
6. test 関連スクリプト定義（package.json / justfile / Makefile / CI）
7. モック/テストダブルの仕組み（MSW, testcontainers, wiremock, 自前モック等）
8. Terraform の場合: validate / plan / tflint / conftest / terratest 相当の有無と CI 接続

出力: モジュールごとに「テスト状況」を表形式で整理し、事実のみ返す。ファイルパス・数値を明記。
```

## 調査 C: 個人環境の棚卸し（オプション・リポジトリ横断で 1 回のみ）

リポジトリ単位の調査とは独立に、個人ハーネス資産のチーム昇格候補を洗い出す場合に実行する。
対象はユーザーのホームディレクトリ配下（リポジトリ外）。

```
対象: ~/.claude/skills/、~/.claude/projects/**/memory/、dotfiles の .config/claude-code/（rules/, skills/）

個人ハーネス資産を棚卸しし、以下を事実ベースで分類してください。

1. 個人 skills の一覧: 各 skill の用途と、直近の使用実績が推定できる情報（更新日時等）
2. 未使用・陳腐化の疑いがある skills（削除候補）
3. チーム昇格候補: 特定リポジトリ・チームの作業に固有で、リポジトリの .claude/skills/ へ移設すると
   チーム全員が使える skills
4. 個人メモリ（MEMORY.md + 詳細ファイル）のうち:
   - 不要・陳腐化しているもの（削除候補）
   - チームの Skills / Hooks / 規約文書へ昇格すべきもの（個人の記憶ではなくチーム共有財産にすべき知見）
5. dotfiles のグローバルルールのうち、リポジトリ規約に昇格すべきもの

出力: 「維持 / 削除候補 / チーム昇格候補（昇格先: skill | hook | 規約文書）」の 3 分類で表にして返す。
ファイルパスを明記。削除・移設は行わない（提案のみ）。
```

## 調査 B'（文書リポジトリ用の置き換え）

```
対象リポジトリ: <REPO_PATH>（手順書・文書リポジトリ）

このリポジトリの文書資産を very thorough に棚卸ししてください。目的は文書資産の統治・移設計画（account-service#4228 の HOTL 統治設計）の材料集めです。

調査対象:
1. ディレクトリ構造と文書の分類（テンプレート / 実施記録 / 設定 / その他）
2. .claude/ のスキル・条件付きルール一覧と各概要
3. テンプレートの種類と数、最終更新時期
4. 実施記録の年代範囲と件数
5. 文書の生成・検証を行う CI やスクリプトの有無

出力: 事実のみを構造化して返す。ファイルパスと件数を明記。
```
