# HOTL 統治モデル定義（ギャップ分類・Phase・6 次元スコアカード）

**本ファイルがギャップ分類（G1〜G8）・Phase（0〜7）・6 次元スコアの定義の基準（SSoT）**。
手順書の「Issue 対応」列のマッピングと仮スコアリングはすべてここの定義を使う。

出典: Visional (BizReach) の [AIE2026 発表「AI駆動開発における統治構造」](https://speakerdeck.com/visional_engineering_and_design/aie2026)
が提唱する HOTL (Human-on-the-Loop) モデル。
人間がフロー内部で逐次判断する HITL から、ループ外部から監督する HOTL へ移行し、
制御位置を「承認者」から「監督者」に変えることを目指す。

## HOTL 自己診断の 3 問

1. **判断根拠の機械可読性 (Q1)** — 違反したら CI が落ちる / Agent が止まるか？
2. **原典と派生の区別 (Q2)** — 自動生成情報が判断根拠になっていないか？
3. **ルール・検証・実行の接続可追跡性 (Q3)** — Agent が追跡し、違反を検知できるか？

核心指標は **AI 実行密度** = AI エージェントが人間の介入なしに自律的に走り続けられる「密度」。

## ギャップ分類 G1〜G8

手順書のギャップ（H 番号）はこの分類にマッピングする。

| # | ギャップ | 内容 | HOTL 三問 |
|---|---|---|---|
| G1 | 憲法層がない | 普遍的開発原則が個別のルール文書に散在し、三権（立法/司法/行政）を拘束する上位文書がない | 前提 |
| G2 | ADR がない | 設計判断がルール文書やコード内に埋没し、判断の経緯を追跡できない | 前提 |
| G3 | ルールが機械可読でない | ルール文書は Agent の参考にはなるが、違反が CI を落とさないものが多い | Q1 |
| G4 | SSoT と派生データの区別がない | 原典と自動生成物が形式的に分離されておらず、派生物が判断根拠に使われうる | Q2 |
| G5 | Authority Provenance Graph がない | ルール↔チェック（CI/lint 等）の双方向追跡がない | Q3 |
| G6 | Specification Provenance Graph がない | 仕様（Issue）→実装→テスト→影響範囲の追跡がない | Q3 |
| G7 | AI 実行密度が計測されていない | Agent の自律走行距離が不明で、ガードレール最適化の根拠がない | 指標 |
| G8 | プロジェクト横断の統治一貫性がない | 各リポジトリが個別にルールを持ち、重複・矛盾がある | 全体 |

## Phase 0〜7（着手順序）

| Phase | 名称 | 目的 | 対応ギャップ |
|---|---|---|---|
| 0 | 計測フレームワーク | スコアカードを整備し、初回スコアリングで現在地を定量化する | — |
| 1 | 憲法層 + ADR 基盤 | 普遍原則の抽出（CONSTITUTION）、軽量 ADR、SSoT レジストリの整備 | G1, G2, G4 |
| 2 | ルールの機械可読化 | 「書かれている」を「効いている」に変える（lint:commit-msg 等の CI ジョブ化、破壊的操作ガードの整備） | G3 |
| 3 | Authority Provenance Graph | ルール↔チェックの双方向追跡（追跡マトリクス、rules への provenance 付与、リンク切れ検出） | G5 |
| 4 | Specification Provenance Graph | Issue テンプレートの Traceability 化、Impact Analysis、レビューでの検証 | G6 |
| 5 | 横断統治の一貫性 | 共有 CI テンプレート、.claude/ 標準構造、共通ルールの上位文書への昇格 | G8 |
| 6 | 観測性 + AI 実行密度計測 | セッションログからの実行密度計測、Agent 観測、セルフアセスメント自動化 | G7 |
| 7 | HOTL 定常運用 | 計測データに基づく介入点の解消と段階的自律拡大（リスク保有者の指名を前提） | — |

着手順序の理由: 測る枠を作る (0) → ルールを書く (1) → ルールを効かせる (2)
→ ルール↔チェックを繋ぐ (3) → 仕様→テストを繋ぐ (4) → 組織で揃える (5)
→ 実データで測る (6) → 移行する (7)。
1→2 と 2→3 は直列（存在しないルールは機械化できず、強制手段のないルールの Provenance は追跡しても意味がない）。
3 と 4 は一部並行可能。

## 6 次元スコアカード（各 0〜3、合計 /18）

仮スコアリングは以下の判定基準で行う。

### 次元 1: 判断根拠の機械可読性 (Q1)

| Level | 定義 | 判定基準 |
|---|---|---|
| 0 | ルールが文書にしかない | ルール文書はあるが CI / Agent が参照・強制しない |
| 1 | 一部が機械強制される | lint / pre-commit で一部のルールが強制される |
| 2 | 大半が機械強制される | ルール文書の 70% 以上に対応する CI チェックがある |
| 3 | 全ルールが機械強制される | ルール追加 = チェック追加が組織プロセスに組み込まれている |

### 次元 2: 原典と派生の区別 (Q2)

| Level | 定義 | 判定基準 |
|---|---|---|
| 0 | 区別がない | SSoT と自動生成物が混在し、どちらが原典か不明 |
| 1 | 暗黙の区別 | 開発者は知っているが文書化されていない |
| 2 | 明示的な区別 | SSoT レジストリが存在し Agent に注入される |
| 3 | 機械的に強制 | 派生データを判断根拠に使おうとすると Agent / CI が警告する |

### 次元 3: ルール・検証・実行の追跡性 (Q3)

| Level | 定義 | 判定基準 |
|---|---|---|
| 0 | 追跡なし | ルールとチェックが独立して存在し対応関係が不明 |
| 1 | 片方向の追跡 | ルール→チェック or チェック→ルールのどちらかが辿れる |
| 2 | 双方向の追跡 | Authority Provenance Graph でルール↔チェックが双方向リンク |
| 3 | 追跡が自動維持 | リンク切れを CI が検出し新規ルール追加時に追跡が強制される |

### 次元 4: 仕様追跡性（Specification Provenance）

| Level | 定義 | 判定基準 |
|---|---|---|
| 0 | 追跡なし | Issue と実装の対応が人間の記憶に依存 |
| 1 | 命名規約による追跡 | ブランチ名 / コミットメッセージに Issue 番号 |
| 2 | 構造的な追跡 | Issue に影響パッケージ・テスト対象が明記、MR で検証 |
| 3 | 影響分析の自動化 | 変更時に影響範囲が自動算出されレビューに反映 |

### 次元 5: AI 実行密度

| Level | 定義 | 判定基準 |
|---|---|---|
| 0 | 計測なし | Agent の自律走行距離が不明 |
| 1 | 手動計測 | セッションログから手動で実行密度を算出できる |
| 2 | 自動計測 | スキルまたは CI で実行密度が定期計測される |
| 3 | 密度に基づく改善 | 計測結果を元にガードレール / パーミッションを最適化するサイクルが回っている |

### 次元 6: 横断統治の一貫性

| Level | 定義 | 判定基準 |
|---|---|---|
| 0 | プロジェクトごとに独立 | 各プロジェクトが個別にルールを定義、重複・矛盾あり |
| 1 | 共通原則が文書化 | 上位の普遍原則文書（CONSTITUTION 等）が存在し各プロジェクトが参照 |
| 2 | 共通ルールが機械的に配布 | CI テンプレート共有、`.claude/rules/` の標準構造 |
| 3 | 逸脱が ADR で管理 | プロジェクト固有ルールの理由が ADR に記録され CI で検証 |
