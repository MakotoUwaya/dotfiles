# 手順書の出力フォーマット

**本ファイルが手順書フォーマットの基準（SSoT）**。グループ・プロジェクト・リポジトリを問わず、
すべての調査でこの §構成と表の列を使う（横断比較のため変えない）。
ギャップ定義（G1〜G8）・Phase・6 次元スコアの定義は account-service#4228 本文を正とする。

## H 番号（ギャップ）の粒度基準

- H 番号はリポジトリごとに H1 から連番で振る（リポジトリ間で番号の対応は取らない）
- 1 ギャップ = **独立して着手できる 1 是正単位**（1 CI ジョブの追加、1 設定/フックの整備、
  1 文書/レジストリの整備が目安）。複数の是正が必要なものは分割する
- 各ギャップには「現状の事実」（ファイルパス・実測値付き）と G1〜G8 / Phase のマッピングを必ず付ける
- 件数の目安は 10〜15 件。細かすぎる列挙（個別 lint ルール単位等）や
  粗すぎる括り（「CI が弱い」等）は避ける

## ギャップ検出の必須観点（AI オートメーション下地・2026-07-03 Slack 指針より）

§1.2 のギャップ洗い出しでは、テスト・CI に加えて以下 4 観点を必ず確認する
（該当ギャップが無ければ「充足」として §1.1 に記載する）:

1. **Skills / Hooks / メモリの棚卸し状況** — 未使用・重複 skills の有無、hooks の整備状況、
   個人資産（skills / メモリ）にチーム昇格候補が滞留していないか
2. **ナレッジの二層化** — 機械強制できないルールが人間可読の規約文書にまとまっているか。
   CLAUDE.md がその文書へのポインタ参照になっており、人とエージェントの両方が同じナレッジを使えるか
3. **目的別サブエージェント定義** — 調査用・実装用・レビュー用のサブエージェント定義があり、
   メインエージェントが目的別に起動できる構成か
4. **「型」抽出の運用** — 重い作業・横断作業の完了時に retro/recap してハーネス
   （規約 / Skills / Hooks / Agents）へ「型」を還元する運用があるか。
   未完タスクを plan + Issue（手順・チェックリスト・完了受入要件）に記録して
   下位モデルでも実施可能な状態にする習慣があるか

```markdown
# #4228 対応手順書（<リポジトリ名> 編）

account-service#4228「開発プロセス自律化に向けた統治設計と責任定義」のうち、<リポジトリ名> を対象とした具体的な作業手順。
調査日: <日付>（コードベース実調査に基づく）

## 1. ハーネスギャップ一覧（As-Is 実測）

### 1.1 既にあるもの（強み）
| 要素 | 具体物 |（文脈 / 実行環境 / 司法(CI) / ガードレール / SSoT チェーン の 5 観点）

### 1.2 足りないもの（ギャップ）
| # | ギャップ | 現状の事実 | Issue 対応 |
（H 番号を振る。Issue 対応列は G1〜G8 / Phase X の形式）

### 1.3 バージョンアップ観点の負債（メジャー遅れ）
| 対象 | 現在 | 最新系 | 影響範囲 |

## 2. テスト拡充の順序（安全なバージョンアップのために）
### 2.1 現状の空白（実測）
| モジュール | src | test | 備考 |
### 2.2 優先順位の考え方
（原則: バージョンアップで壊れる境界を先にカバー / 依存の広がり×薄さ×アップグレード予定でスコアリング / snapshot の隙間を挙動テストで埋める）
### 2.3 作成順序
| 順 | 対象 | 作るもの | 守れるようになるバージョンアップ |
（表の後に「順序の理由」を箇条書き）
### 2.4 バージョンアップ実施との関係
（major 承認の条件として「対応テスト層あり」をルール化）

## 3. ルール運用構成（進化に耐える形)
### 3.1 現状の層構造（CLAUDE.md → RULES.md → .claude/rules/ の 3 層を基準に差分を記述）
### 3.2 ルールにメタデータを付ける（ルール ID + enforcement: <CI ジョブ名> | agent-only | human-only、provenance）
### 3.3 ルール変更の運用フロー（追加 / 設計判断 / 削除 / 定期棚卸し）
### 3.4 すぐ着手できる機械化（lint:commit-msg / lint:lockfile / lint:generated-drift 等）
### 3.5 ナレッジの二層化（機械強制できないルール → 人間可読の規約文書 + CLAUDE.md からポインタ参照。人とエージェント両用にする）
### 3.6 Skills・サブエージェント・「型」抽出の整備
（skills 棚卸しの結果と昇格・削除の提案 / 調査用・実装用・レビュー用サブエージェント定義の整備方針 /
重い作業完了時の retro/recap による型抽出と、未完タスクの plan + Issue 記録の運用）

## 4. 実施ステップ（MR 単位の目安）
| Step | 内容 | 本書の節 | Issue Phase |
（並行可能な Step を明記）
```

## スコアカード仮スコア

手順書末尾に 6 次元（Q1 機械可読性 / Q2 原典・派生 / Q3 ルール追跡性 / 仕様追跡性 / AI 実行密度 / 横断一貫性、各 0〜3）の
仮スコアを 1 行表で付記し、#4228 本文の初回スコアリング表との差異があれば「要確認」として明記する。
初回スコアリング表に存在しないリポジトリ（es-account 外等）の場合は、差異比較の代わりに
「#4228 スコープ外・統治スコープへの編入可否は要確認」と明記する。

## 文書リポジトリ（esa-docs 等）の場合

§2 を「移設対象の分類と移設順序」に、§1.3 を「陳腐化した文書・テンプレートの一覧」に置き換える。
§3・§4 は共通。
